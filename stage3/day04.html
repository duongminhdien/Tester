重点二：请求方法（GET vs POST）

维度GETPOST
参数位置URL中（地址栏可见）请求体中（不可见）
安全性较低（参数明文在URL）较高（参数在请求体）
长度限制有限制（约2KB~8KB）无长度限制
可缓存可以缓存/收藏不可缓存
适用场景查询、搜索（不改变数据）登录、注册、提交数据、上传
TPShop示例搜索商品（?keyword=手机）前台/后台登录
🔴 安全测试要点：登录/注册/支付等含敏感信息的表单，必须使用POST。如果发现使用GET传递密码（URL明文可见），这是S1级安全Bug。

重点三：请求参数格式

# GET请求参数在URL中：
GET /search?keyword=手机&page=1&sort=price HTTP/1.1

# POST请求参数在请求体：
POST /api/login HTTP/1.1
Content-Type: application/x-www-form-urlencoded

# 请求体（Body）：
username=13812345678&password=abc123&captcha=AB12

2.2 HTTP 响应（重点：状态码）

状态码类型含义常见状态码测试中的含义
2XX请求成功200（成功），204（无内容）接口正常，功能成功
3XX重定向301（永久），302（临时），304（缓存）页面跳转，通常无问题
4XX客户端错误400（参数错误），401（未授权），403（禁止），404（找不到）前端请求有误
5XX服务器错误500（内部错误），502（网关错误），503（不可用）后端服务故障，Bug
📌 常见状态码记忆：
200 = 成功（最常见的正确响应）
404 = 找不到资源（URL路径错误/资源不存在）
401 = 未授权（未登录就访问需要登录的页面）
403 = 禁止访问（无权限）
500 = 服务器内部错误（后端Bug，最严重）

响应体：服务器返回给客户端的实际数据，常见格式：

# 格式一：HTML（前台页面返回的HTML代码）
<html><body>页面内容</body></html>

# 格式二：JSON（API接口常用，易于程序解析）
{"code": 200, "msg": "登录成功", "data": {"username": "张三"}}

# 格式三：TXT（纯文本）或 图片等二进制数据

HTTP完整通信过程

① 用户操作（客户端）

输入URL → 浏览器发起HTTP请求
包含：方法(GET/POST) + URL + 参数 + 请求头

② 服务器处理

接收请求 → 处理业务逻辑 → 查询/更新数据库 → 生成响应数据

③ 服务器响应

返回：响应状态码 + 响应头 + 响应体（HTML/JSON/图片）

④ 浏览器渲染

解析响应数据 → 渲染页面 → 展示给用户

🌐GET vs POST 核心对比图

GET 请求特征

  • 参数拼在URL后面（? 分隔）
  • 浏览器地址栏可以看到参数
  • URL有长度限制（约2KB）
  • 可以被浏览器缓存
  • 可以被收藏/分享
  • 适合：搜索、查询、翻页
GET /search?q=手机&page=1 HTTP/1.1

POST 请求特征

  • 参数放在请求体（Body）中
  • 地址栏看不到参数（需抓包）
  • 无长度限制
  • 不可缓存
  • 相对更安全
  • 适合：登录、注册、提交、上传
POST /api/login HTTP/1.1
username=abc&password=123

📊HTTP响应状态码速查

状态码名称测试中遇到意味着什么常见场景
200OK - 成功接口正常，功能执行成功登录成功、页面正常加载
204No Content请求成功但无返回内容删除操作成功
301永久重定向URL永久变更，浏览器自动跳转http → https跳转
302临时重定向临时跳转到另一个URL登录后跳转首页
304未修改（缓存）资源未变，浏览器从缓存读取静态文件缓存
400Bad Request请求参数格式错误（前端Bug）表单数据格式不对
401Unauthorized未认证/未登录（需要登录）未登录访问需登录页面
403Forbidden已认证但无权限普通用户访问管理员接口
404Not Found资源不存在（URL错误/已删除）URL路径写错
500Internal Server Error后端代码异常，严重Bug服务器空指针/数据库异常
502Bad Gateway网关/代理收到上游无效响应Nginx无法连接后端服务
503Service Unavailable服务器不可用（过载/维护）高并发时服务崩溃

🔍用Fiddler抓包定位Bug原理

前端Bug特征

  • ❌ 无请求发出（点了没动静）
  • ❌ 请求URL/方法/参数有误
  • ❌ 请求正确，响应正确，但页面显示错误

后端Bug特征

  • ❌ 请求正常，但无响应
  • ❌ 请求正常，响应状态码错误（5XX）
  • ❌ 请求正常，响应数据错误
📌 判断流程：有请求？→ 请求参数对？→ 有响应？→ 状态码对？→ 响应数据对？→ 页面渲染对？
每一步失败，就定位到对应的问题所在（前端/网络/后端/渲染）。

4. 解析URL：https://www.tpshop.com:443/goods?id=123&color=red#detail，说明每个部分的含义
考察URL组成结构
查看答案 ›
URL各部分解析：

• https = 协议（加密的HTTP，端口默认443）
• www.tpshop.com = 主机地址（域名，解析为IP）
• :443 = 端口（https默认443，一般省略不写）
• /goods = 路径（资源的具体地址）
• ? = 路径与参数的分隔符
• id=123 = 参数1（商品ID为123）
• & = 多个参数的分隔符
• color=red = 参数2（颜色为red）
• #detail = 锚点（页面内跳转位置）

常见端口：HTTP=80，HTTPS=443，MySQL=3306，Nginx=80
5. 用Fiddler抓包发现：登录请求正常发出（200响应），但页面提示"登录失败"。这是前端Bug还是后端Bug？
考察前后端Bug定位能力
查看答案 ›
情况分析：请求正常发出 + 状态码200 + 页面提示"登录失败"

需要进一步检查响应体（Response Body）的内容：

情况A（前端Bug）：
响应体中包含"登录成功"的数据（如 {"code":200,"msg":"success"}），但前端错误地显示"登录失败"。
→ 前端处理响应的JavaScript代码有Bug（解析错误/逻辑错误）

情况B（后端Bug）：
响应体中包含"登录失败"的数据（如 {"code":400,"msg":"密码错误"}），HTTP状态码却是200。
→ 后端业务逻辑返回了失败，但HTTP状态码设置为200（不规范但常见）
→ 此时"登录失败"是后端返回的正确信息，需看是否与输入的数据匹配

结论：必须查看响应体内容，才能准确判断是前端还是后端问题。

7. HTTP状态码500和404的含义，测试时分别意味着什么？
考察HTTP状态码的实际应用
查看答案 ›
404 Not Found：
含义：服务器找不到请求的资源（URL错误/资源已删除/服务未启动）
测试时意味着：
① 功能测试中：URL路径配置错误，需要排查前端路由或后端接口地址
② 可能是Bug：点击某个链接/按钮后出现404页面
③ 不一定是Bug：输入不存在的商品ID，合理返回404

500 Internal Server Error：
含义：服务器内部处理出错（代码异常/空指针/数据库连接失败）
测试时意味着：
① 通常是严重Bug（S1级）
② 后端代码有未处理的异常
③ 数据库查询出错
④ 配置文件错误
Bug报告：附上操作步骤、截图（显示500页面）、服务器日志（如能获取）

💬面试精讲（共12题）

涵盖购物车测试、HTTP协议、状态码、GET/POST等高频面试题。

Q1
HTTP请求由哪几部分组成？测试工程师重点关注什么？
基础
+

HTTP请求3个部分：

  • 请求行：请求方法（GET/POST）+ URL + 协议版本
  • 请求头（Headers）：Content-Type、Authorization、Cookie等元数据
  • 请求体（Body）：POST请求的参数数据

测试工程师重点关注（3个）：

  • URL：协议+主机+端口+路径+参数
  • 请求方法：GET/POST是否使用正确（敏感操作必须POST）
  • 请求参数：参数名/值是否正确传递（用于验证前端发送的数据）
Q2
GET和POST有什么区别？（至少说5个）
基础
+

5个核心区别：

  1. 参数位置：GET参数在URL（可见）；POST参数在请求体（不可见）
  2. 安全性：GET安全性低；POST相对安全（但非绝对，HTTPS才算真安全）
  3. 长度限制：GET约2KB限制；POST无限制
  4. 可缓存性：GET可缓存/可收藏；POST不可缓存
  5. 适用场景：GET用于查询（幂等）；POST用于提交/修改数据（非幂等）
💡 补充：相同点是都可以向服务器发送请求并携带参数。
Q3
HTTP响应状态码有哪几类？各自含义是什么？
基础
+
  • 2XX（成功）：请求被服务器成功处理。200=OK，204=无内容
  • 3XX（重定向）：请求需要进一步操作。301=永久重定向，302=临时，304=缓存
  • 4XX（客户端错误）：请求有问题。400=参数错，401=未认证，403=禁止，404=不存在
  • 5XX（服务器错误）：服务器处理失败。500=内部错误，502=网关错，503=不可用
Q4
URL由哪些部分组成？以 http://api.tpshop.com:8080/login?user=abc 为例解析
基础
+

URL格式：协议://主机地址:端口/路径?参数名=参数值&参数名=参数值

解析示例：http://api.tpshop.com:8080/login?user=abc

  • http = 协议（传输格式，如http/https/ftp）
  • api.tpshop.com = 主机地址（域名/IP）
  • 8080 = 端口号（http默认80可省略，8080需写明）
  • /login = 路径（资源的具体地址）
  • ? = 路径与参数的分隔符
  • user=abc = 参数（键=值，多个参数用&分隔）
Q5
购物车小计/总价/已节省的计算公式是什么？如何验证？
基础
+

三个计算公式：

  • 小计 = 商品单价 × 购买数量
  • 总价 = 所有已勾选商品的小计之和
  • 已节省 = Σ（原价 - 活动价）× 数量（仅计算已勾选的活动商品）
  • 已选N件 = 已勾选商品的数量总和（非种类数）

验证方法：

  1. 手动计算期望值（用计算器）
  2. 与页面显示值对比
  3. 通过勾选/取消勾选、修改数量，验证各值实时正确更新

Q7
什么是抓包？Fiddler的工作原理是什么？
基础
+

抓包（Packet Capture）：通过工具拦截客户端与服务器交互的数据包，查看HTTP请求和响应的详细内容。

Fiddler工作原理：

  • Fiddler作为代理服务器，处于浏览器和服务器之间
  • 浏览器将请求发给Fiddler（代理），Fiddler转发给服务器
  • 服务器响应返回给Fiddler，Fiddler转发给浏览器并记录
  • Fiddler可以查看、修改、重放所有HTTP通信内容

测试中的3大用途：① 定位前后端Bug ② 弱网测试 ③ 绕过界面限制测试

Q11
【陷阱题】用户已登录，加入购物车操作返回200状态码，但购物车列表没有新商品。这是前端Bug还是后端Bug？
高阶
+

需要看响应体内容才能判断：

情况A（后端Bug）：
响应体中的code字段是失败码（如 {"code":400,"msg":"库存不足"}），但HTTP状态码写成了200。
→ 后端没有把商品加入购物车，且HTTP状态码不规范。实际是后端业务逻辑Bug。

情况B（前端Bug）：
响应体中的code是成功（{"code":200,"msg":"加入成功"}），但前端没有刷新购物车列表。
→ 后端成功加入了购物车，前端没有更新UI。属于前端渲染/状态更新Bug。

情况C（前端Bug）：
响应体中的code是成功，但购物车列表查询是另一个接口，该接口没有被重新调用。
→ 前端没有在加购成功后触发刷新购物车列表的请求。

💡 结论：200状态码≠功能成功。必须检查响应体中的业务状态码（code字段）和实际数据。

✅测验（共15题）

考察购物车完整测试 + HTTP协议知识。

1购物车"小计"的正确计算公式是？
✅ 正确答案：B – 小计 = 单价 × 数量（针对单个商品）。总价 = 所有已勾选商品的小计之和。修改某商品数量后，该商品小计和购物车总价都应实时更新。
2购物车"已选N件商品"中，N的含义是？
✅ 正确答案：B – N = 已勾选商品的数量总和。如勾选商品A（3件）和商品B（2件）→ N=5。注意是数量之和，不是种类数，也不包含未勾选的商品。
3购物车单个商品数量的上限是多少？超出后如何？
✅ 正确答案：B – 上限是200件或库存数量，取较小值。超出200或超出库存时，【+】按钮失效。直接输入超过200的数字时应给出提示，不能成功添加。
4购物车商品种类的最大限制是多少种？
✅ 正确答案：C – 购物车商品种类不能大于20种，超出时给出提示。边界值：第20种成功（上点），第21种应被拒绝（离点）。
5GET和POST的核心区别，哪个描述是错误的？
✅ 正确答案：C – GET和POST都可以向服务器发送请求并携带参数，这是两者的相同点。GET参数在URL里，POST参数在请求体里。C选项说"都不能发送参数"是错误的。
6URL中多个参数之间用什么符号分隔？路径和参数之间用什么分隔？
✅ 正确答案：B – URL格式：路径?参数名=参数值&参数名=参数值。路径和参数之间用?分隔，多个参数之间用&分隔。例：/search?q=手机&page=1&sort=price。
7HTTP状态码404的含义是？测试时遇到意味着什么？
✅ 正确答案：B – 404 Not Found：服务器找不到请求的资源。可能是URL路径错误、资源已删除、服务未启动。测试时点击链接/按钮出现404页面，通常是Bug（路由配置错误）。
8测试购物车时，发现页面报500错误，正确的处理方式是？
✅ 正确答案：B – 500是服务器内部错误，通常是严重Bug（S1级）。需要：确认稳定复现 → 提Bug（S1优先级）→ 附操作步骤+Fiddler截图+服务器日志（如能获取）。
9购物车"已节省"的计算公式是？
✅ 正确答案：B – 已节省 = 所有已勾选活动商品的节省金额之和 = Σ（原价-活动价）× 数量。只计算参与促销活动的商品，普通商品不计入（节省=0）。取消勾选活动商品后已节省金额归零。

✅ 正确答案：B – 需求规定：同时结算多家店铺商品，会产生对应店铺数量的订单（订单数=店铺数）。2家店铺 → 2个订单。这是测试用例tp_cart_011的验证点。

✅ 正确答案：B – 2XX=成功（200/204），3XX=重定向，4XX=客户端错误（400/401/403/404），5XX=服务器错误（500/502/503）。记忆：4XX是用户的问题，5XX是服务器的问题。
