🔍一、Fiddler 抓包工具实战应用

Fiddler 定义：Fiddler 是一个 HTTP 协议调试代理工具，能够记录并检查所有客户端与互联网之间的 HTTP 通信。

原理：Fiddler 作为代理服务器，位于浏览器和服务器之间，所有请求和响应都经过 Fiddler 中转，因此可以拦截、查看、修改数据包。

Fiddler 基本操作

🔽 过滤（Filters）

只看指定域名的请求，避免被其他网站干扰。

Filters→ 勾选 Use Filters→ Show only the following Hosts→ 输入域名/IP→ Actions → Run Filterset Now

🗑️ 删除数据

方式一：点击工具栏 Remove all（删除全部）
方式二：在底部黑窗口输入 cls 回车
方式三：选中某条 → 右键 → Remove

🔎 查看数据包内容

选中数据包（或双击）→ 点击 Inspectors → 请求内容点击 Raw（行\头\体）→ 响应内容点击 Raw

场景1：定位前后端 Bug

📌 判断流程：打开Fiddler → 操作功能 → 观察请求和响应 → 判断问题在前端还是后端
Bug位置Fiddler中的表现举例
前端Bug① 无请求发出
② 请求URL/方法/参数有误
③ 响应正确但页面显示错误		点击按钮无请求；密码用GET明文传；响应成功但页面提示失败
后端Bug① 请求正常，无响应
② 响应状态码5XX
③ 响应数据内容错误		接口返回500；接口返回的数据字段值错误

场景2：弱网测试

模拟弱网（2G/3G/4G）环境，验证应用在低速网络下的稳定性。

⚠️ 弱网下常见问题：① 上传文件进度卡住不动 ② 登录不上或登录后立即掉线 ③ 响应过程中页面控件可点击导致崩溃 ④ 搜索不响应，多次点击结果总在刷新被替换
1
设置网络速度（延迟参数）

Rules → Customize Rules → Ctrl+F 搜索 "300" → 找到 m_SimulateModem → 修改 request-trickle-delay（上行）和 response-trickle-delay（下行），单位：每KB延迟多少ms

2
开启网络延迟

Rules → Performance → Simulate Modem Speeds（勾选开启）

3
执行测试

在模拟的弱网环境下操作功能，观察并记录异常

4
恢复设置

测试完成后，取消勾选 Simulate Modem Speeds，恢复正常网络速度

📌 课堂弱网参数：上行（request-trickle-delay）= 3000，下行（response-trickle-delay）= 1500，单位 ms（每 1KB 数据延迟的毫秒数）
延时计算公式：延时(ms) = [1/(速率bps/8)] × 1000。1s = 1000ms，1KB = 1024B = 8192bit

场景3：绕过界面限制直接测试服务器

目的：前端对输入有限制（如字数限制、只能选择等），需要测试服务器对非法数据的处理能力。

1
设置断点（请求之前）

Rules → Automatic Breakpoints → Before Requests（快捷键 F11）

2
触发请求

在页面上正常操作（如点击提交），请求会被 Fiddler 拦截暂停

3
修改请求参数

在 Fiddler 的 Inspectors → WebForms 或 Raw 中修改请求体参数，注入非法数据

4
放行请求

点击 Run to Completion，将修改后的请求发送给服务器

5
（可选）设置响应断点

Rules → Automatic Breakpoints → After Responses（Alt+F11），可修改响应内容再返回浏览器

⚠️ 响应修改注意：如果响应体是编码状态，需要先点击 "Response body is encoded. Click to decode."，解码后再修改响应数据，最后点击 Run to Completion。

1. Fiddler的工作原理是什么？与普通浏览器网络面板（F12）的区别？
考察Fiddler的基础理论理解
查看答案 ›
Fiddler工作原理：代理服务器模式
浏览器 → 发请求到Fiddler（代理）→ Fiddler转发给服务器 → 服务器响应返回Fiddler → Fiddler转发给浏览器。所有HTTP通信经过Fiddler，因此可以查看、修改、重放。

与F12 Network的区别：
F12（开发者工具）：浏览器内置，只能看当前浏览器的请求，无法修改请求，只能查看不能拦截
Fiddler：系统级代理，可以抓取所有应用的HTTP请求（包括手机APP、桌面应用），可以拦截并修改请求/响应，功能更强大

使用场景：F12适合前端调试；Fiddler适合测试接口、弱网测试、绕过前端限制。
2. 如何使用Fiddler过滤只显示TPShop的请求？完整操作步骤是什么？
考察Fiddler过滤功能的实际操作
查看答案 ›
完整操作步骤：
1. 打开Fiddler，点击菜单栏 Filters 标签（非Filters菜单，是右侧面板的标签）
2. 勾选 Use Filters（启用过滤）
3. 第二个下拉框选择 "Show only the following Hosts"
4. 在输入框中输入TPShop的域名或IP地址（如：hmshop-test.itheima.net）
5. 点击 Actions → Run Filterset Now（立即生效）

效果：Fiddler只显示来自该域名的请求，其他网站的请求被隐藏，方便聚焦测试目标。

清除过滤：取消勾选 Use Filters，或将下拉框改回 "No Zone Filter"。
3. 弱网测试中，如何设置上行3000ms下行1500ms的延迟？完整步骤？
考察弱网测试操作流程
查看答案 ›
步骤一：设置延迟参数
1. Fiddler菜单：Rules → Customize Rules（或按Ctrl+R）
2. 打开FiddlerScript编辑器
3. 按Ctrl+F搜索"300"，找到 m_SimulateModem 代码块

  • response-trickle-delay = "1500"（下行延迟：每KB下载需要1500ms）
5. Ctrl+S 保存脚本

步骤二：开启弱网模拟
Rules → Performance → Simulate Modem Speeds（勾选）

步骤三：执行测试
在弱网环境下操作功能，观察卡顿/崩溃/异常等问题

步骤四：恢复正常
测试完成后，取消勾选 Simulate Modem Speeds

6. Bug的严重等级S0/S1/S2/S3分别对应什么上线标准？举例说明
考察Bug严重等级与上线判断标准
查看答案 ›
四个等级及上线标准：

S0（致命）：100%必须修复才能上线
示例：系统崩溃、内存泄漏、用户无法登录、主流程完全不可用

S1（严重）：100%必须修复才能上线

7. 灰度发布的定义是什么？为什么要做灰度发布？
考察对上线策略的理解
查看答案 ›
灰度发布定义：在正式全量发布生产环境之前，先将新版本部署到1~3台服务器上（占总服务器的少数），让少量真实用户先体验新版本，验证功能是否正常。

为什么做灰度发布：
1. 降低风险：新版本问题只影响少量用户，而不是所有用户
2. 快速回滚：如果新功能有问题，只需回滚少数几台服务器，操作简单
3. 真实环境验证：预生产环境再好，真实用户数据/行为可能暴露新问题
4. 减少损失：相比全量上线出问题，灰度发布失败的损失更小

流程：预生产通过 → 灰度发布（1~3台）→ 观察7天 → OK则全量发布 → 有问题则回滚

• http：明文传输，不加密，不安全，端口80
• https：加密传输（SSL/TLS），安全，端口443，需要SSL证书

测试判断标准（何时必须用https）：
1. 涉及用户密码的传输（登录/注册/修改密码）
2. 涉及支付信息（银行卡号/CVV）
3. 涉及个人隐私（身份证/手机号）
4. 正式生产环境的所有接口

测试要点：用Fiddler检查登录接口是否使用HTTPS；如果密码通过HTTP明文传输 → S1安全Bug。
如果使用HTTPS，Fiddler需要安装证书才能解密查看内容（默认只显示CONNECT隧道）。

Q1
Fiddler的工作原理是什么？有哪3大使用场景？
基础
+

工作原理：Fiddler作为代理服务器，位于浏览器和目标服务器之间。浏览器将请求发给Fiddler，Fiddler转发给服务器，服务器响应经过Fiddler再返回浏览器。所有HTTP通信都在Fiddler中留有记录，可以查看、修改、重放。

3大使用场景：

  1. 定位前后端Bug：通过查看请求和响应内容，判断问题是前端（无请求/参数错/显示错）还是后端（无响应/5XX/数据错）
  2. 弱网测试：模拟低速网络环境（2G/3G），验证应用在弱网下的稳定性
  3. 绕过界面限制测试：拦截请求修改参数，绕过前端校验，测试后端对非法数据的处理
Q2
http和https有什么区别？（高频面试题）
基础
+

共同点：都是协议，都可以用来传输数据。

不同点：

  • 安全性：HTTP明文不加密，HTTPS使用SSL/TLS加密，更安全
  • 端口：HTTP默认80，HTTPS默认443
  • 证书：HTTPS需要SSL证书，HTTP不需要
  • 使用场景：生产环境（尤其含敏感数据）必须用HTTPS；开发/测试环境可用HTTP
🔴 测试要点：登录/支付等涉及敏感数据的接口必须使用HTTPS。如果用HTTP传输密码 → S1安全Bug。
Q3
测试报告的作用是什么？主要包含哪些内容？
基础
+

作用：汇总测试结果，评估产品质量，为管理层提供上线决策依据。是测试阶段最终的输出产物。

5大章节内容：

  1. 测试项目概述（背景/目的/参考资料）
  2. 测试回顾（环境/进度/统计）
  3. Bug统计分析（分布图/统计表/遗留清单）
  4. 测试整体总结（模块评价/最终结论）
  5. 总结建议（经验总结/风险）
Q4
弱网测试的目的是什么？常见的弱网问题有哪些？
基础
+

目的：验证应用在低速网络（2G/3G/WiFi信号差）环境下的稳定性和用户体验，发现正常网速下不易暴露的问题。

常见弱网问题：

  • 上传文件时进度条卡住不动
  • 登录不上或登录后立即掉线
  • 响应过程中页面控件已可点击，导致崩溃
  • 搜索不响应，多次点击后结果总在刷新被替换
  • 图片加载超时，显示默认占位图
  • 支付流程超时后，订单状态不确定
Q5
如何判断一个Bug是前端问题还是后端问题？（面试高频）
进阶
+

需要借助Fiddler/抓包工具分析HTTP请求和响应：

前端Bug的表现：

  • ① 无请求发出（按钮点击但无HTTP请求）
  • ② 请求参数错误（URL/方法/参数有误）
  • ③ 请求正确+响应正确，但页面显示错误

后端Bug的表现：

  • ① 请求正常发出，但无响应
  • ② 响应状态码为5XX（服务器内部错误）
  • ③ 响应状态码200但响应体中的业务数据错误
💡 判断流程：有请求？→ 请求参数对？→ 有响应？→ 状态码对？→ 响应体数据对？→ 页面渲染对？每步失败对应不同的问题层次。
Q6
什么是灰度发布？为什么要做灰度发布？
进阶
+

灰度发布：在全量发布生产环境前，先将新版本部署到少数服务器（1~3台），让少量真实用户先体验，验证功能正常后再全量发布。

原因：生产服务器通常有多台，一旦新功能有问题，全量发布会影响所有用户，损失巨大。灰度发布先在少数台验证，失败时只需回滚少数台，影响最小。

典型流程：开发环境 → 测试环境 → 预生产环境 → 灰度发布（1~3台生产服务器）→ 观察OK → 全量发布

Q7
绕过界面限制测试的目的是什么？何时需要用这种方法？
进阶
+

目的：前端界面对用户输入进行了限制（如：数量最多输入200，通过UI无法输入201），但后端服务器是否也有校验是未知的。绕过前端限制，直接测试后端对非法数据的处理能力。

何时使用：

  • 数字输入框有最大值限制（如200件）
  • 文本框有最大字数限制
  • 下拉框只能选择预设值
  • 需要测试服务器端校验是否完整

测试价值：如果后端没有对应校验，攻击者可以通过抓包工具绕过前端限制，直接发送非法请求，导致数据异常或安全漏洞。这类测试非常重要。

Q9
敏捷开发和传统瀑布开发对测试工程师的影响？

瀑布开发（传统）：需求→设计→开发→测试→发布，各阶段顺序执行，测试在最后才介入，问题发现晚，修复成本高。

  • 回归测试频率高（每个Sprint都要回归），可能需要自动化辅助
  • 测试报告变为迭代报告而非项目最终报告

Q11
【场景题】用Fiddler发现：某功能点击后，Fiddler里看到有请求（200），但页面提示"操作失败"，是前端还是后端Bug？
高阶
+

有请求+状态码200+页面提示失败，需要进一步检查响应体内容：

情况A（后端Bug）：响应体中的业务码是失败（如 {"code":400, "msg":"操作失败"}），HTTP状态码是200只是HTTP层面成功，但业务层面失败了。→ 后端业务逻辑处理出错。

情况B（前端Bug）：响应体中业务码是成功（{"code":200,"msg":"success"}），但前端解析响应时出错，错误地显示了"操作失败"。→ 前端JS处理响应逻辑有Bug。

💡 关键原则：HTTP状态码200 ≠ 业务成功。必须同时检查响应体中的业务状态码（code字段）才能准确判断。

✅测验（共15题）

考察Fiddler抓包、弱网测试、绕过限制、测试报告、http/https、APP基础知识。

1Fiddler工作的原理是？
✅ 正确答案：B – Fiddler作为代理服务器：浏览器→Fiddler→服务器→Fiddler→浏览器。所有HTTP通信都经过Fiddler，所以可以查看、修改、重放数据包。
2Fiddler中，只查看TPShop域名的请求，需要使用哪个功能？
✅ 正确答案：C – Filters → 勾选Use Filters → Show only the following Hosts → 输入域名 → Actions → Run Filterset Now。这样只显示目标域名的请求，避免被其他请求干扰。
3弱网测试中，开启网络延迟模拟的操作路径是？
✅ 正确答案：B – 弱网测试步骤：先Rules→Customize Rules修改延迟参数值，然后Rules→Performance→Simulate Modem Speeds开启。测试结束记得关闭，避免影响后续正常测试。
4绕过界面限制，设置请求断点（请求之前）的操作路径是？
✅ 正确答案：B – Before Requests（F11）在请求发出前拦截，可以修改请求参数再放行。After Responses（Alt+F11）在响应返回后拦截，可以修改响应数据。修改后点击Run to Completion放行。
5用Fiddler定位Bug时，发现点击按钮后Fiddler里没有任何请求，这说明是？
✅ 正确答案：B – 无请求=前端Bug。请求是从浏览器发出的，如果Fiddler没有捕获到任何请求，说明浏览器根本没有发出HTTP请求，问题在前端（JS事件未绑定/脚本错误/逻辑未执行）。
6http和https的主要区别是？
✅ 正确答案：B – http：明文不加密，端口80，不安全；https：SSL/TLS加密，端口443，安全。共同点：都是协议，都能传输数据。生产环境含敏感数据必须使用https。
7测试报告第3章"Bug统计分析"应该包含哪些内容？
✅ 正确答案：B – 第3章包含：3.1 Bug统计（饼图+表格+版本趋势柱状图）、3.2 Bug分析（判断数据是否正常，异常版本原因分析）、3.3 遗留问题清单（未修复Bug的详细信息）。
8S0（致命）Bug的上线标准解决率要求是多少？
✅ 正确答案：C – S0和S1级Bug：上线前必须100%解决；S2级：≥95%；S3级：可全部遗留。S0 Bug留一个不修复就不能上线，这是测试的基本底线。
9灰度发布的核心好处是？
✅ 正确答案：B – 灰度发布先在1~3台服务器验证，有问题只需回滚少数台，影响少量用户。相比全量发布出问题（影响所有用户），灰度发布损失最小，是稳健的上线策略。
10Android软件安装包的格式是？
✅ 正确答案：C – Android = .apk（Android Package Kit）；iOS = .ipa；Windows = .exe；macOS = .dmg。测试时给测试人员的Android包是.apk，可以直接拖入雷电模拟器安装。
11测试报告的"测试回顾"章节需要包含哪3个部分？
✅ 正确答案：B – 第2章测试回顾：2.1测试环境（硬件/软件/网络配置）、2.2进度回顾（各阶段时间/人员/产物）、2.3测试统计（用例总数/执行率/Bug数及分类）。
12弱网测试中，弱网延迟参数的单位是什么？delay=3000代表什么含义？
✅ 正确答案：B – 单位是毫秒/KB：request-trickle-delay=3000 表示每上传1KB数据延迟3000ms；response-trickle-delay=1500 表示每下载1KB延迟1500ms。文件越大，延迟越明显，模拟弱网效果越真实。
13测试报告的最终结论（4.2测试结果）有哪几个选项？
✅ 正确答案：B – 测试结果三选一：■全部通过（所有用例通过，无遗留Bug）□部分通过（有遗留Bug但满足准出标准）□都不通过（严重问题未解决）。TPShop示例是"■部分通过"。
14ADB（Android Debug Bridge）的主要用途是？
✅ 正确答案：B – ADB = Android Debug Bridge，是Android SDK的命令行工具，用于PC与Android设备通信：安装/卸载APK、查看logcat日志、传输文件、截图等。配置：将platform-tools路径加入系统Path，cmd输入adb验证。
15【场景题】Fiddler中发现某接口响应状态码是200，但业务数据中code=500，msg="服务器错误"。这是哪类Bug？Bug描述怎么写？
✅ 正确答案：B – HTTP状态码200表示HTTP层面传输成功，但响应体中code=500表示业务逻辑失败。这是后端Bug：① 业务处理失败本身是Bug ② HTTP状态码应返回5XX而非200（不规范）。Bug标题示例：「【接口名称】接口响应HTTP 200但业务code=500，msg="服务器错误"，功能无法正常使用」。
